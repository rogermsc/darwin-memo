## Why we are writing

We are writing a paper on *curation-targeted attacks*: attacks that corrupt the
signal a memory curator decides on, rather than injecting poisoned content. Our
survey of deployed agent-memory systems found that most do not curate
mechanically at all — Graphiti and Letta decline to remove on their automatic
paths, Cognee removes only when a caller asks, Mem0 removes only when a model
agrees. MemoryOS was the one system we found whose curator **removes entries by
a rule, from a measured signal**, which makes it the only deployed target our
threat model actually applies to.

We think two of the three findings below are design trade-offs worth documenting
rather than vulnerabilities, and one is a straightforward robustness bug. **None
of them is a remote-code-execution or data-exfiltration issue.** We would rather
send this before publication than after, and we are happy to correct anything we
have got wrong about the code.

## Finding 1 — heat-triggered promotion costs three self-queries (design)

`MidTermMemory` promotes a session's content into long-term memory when its
heat crosses `H_PROFILE_UPDATE_THRESHOLD` (`memoryos.py:26`, `5.0`). Heat is
`compute_segment_heat` (`mid_term.py:26-36`):

```python
return alpha * N_visit + beta * L_interaction + gamma * R_recency
```

with `HEAT_ALPHA = HEAT_BETA = 1.0` and `HEAT_GAMMA = 1` (`mid_term.py:21-23`),
so the threshold is plain arithmetic. A session holding one page starts at
`L_interaction = 1`, `R_recency = 1.0`, `N_visit = 0`; each retrieval increments
`N_visit`, so heat runs 3.0 → 4.0 → 5.0 and crosses on the **third retrieval**.
Long-term memory is a tier capacity pressure never evicts from.

So a party who can get any content into mid-term storage and then ask about it
three times has the curator copy that content into the persistent tier. No
delete call, no judge, no further writes.

We demonstrated this end to end. A canary string appearing only in the
adversary's turn reached MemoryOS's long-term **user knowledge** in 3/3 trials
and assistant knowledge in 2/3, against a control that adds the same turn and
never asks about it (heat 2.0, never promotes, 0/3). We did **not** call
`force_mid_term_analysis`, which would have bypassed the threshold entirely, and
we lowered no threshold.

*Why we call this a trade-off rather than a bug:* promotion on repeated use is
the intended behaviour. What we think is worth documenting is how cheap the
threshold is in adversarial terms — three questions — and that the promoted tier
has no eviction path.

## Finding 2 — a single retrieval confers permanent immunity from eviction (design)

`MidTermMemory.evict_lfu` selects `min(self.access_frequency, key=...)`
(`mid_term.py:75`) and nothing else — no model is asked and no text is read.
`add_session` sets `self.access_frequency[session_id] = 0` and only then runs
`if len(self.sessions) > self.max_capacity: self.evict_lfu()`
(`mid_term.py:172-177`), so every arrival sits at the floor when eviction
happens. Sweeping the victim over every seeded memory, eviction tracked one
bit exactly: **evicted if and only if `access_frequency` is zero.** All 3 victims
that reached zero were evicted; none of the 9 retrieved even once ever was.

Two consequences:

1. A memory retrieved even once cannot be removed by capacity pressure at all.
2. Because `min` returns the first minimum in insertion order, a never-retrieved
   memory loses to a brand-new arrival that is *also* at zero. MemoryOS evicts
   the memory nobody has asked for yet in preference to the one that arrived a
   moment ago.

This is the rare-but-critical case: an emergency contact or an allergy note is
precisely the memory stored once, needed rarely, never consulted in between —
and it is first out. We note in our own paper that our mechanism has the same
exposure and answers it with pinning (flooring a pinned entry's balance instead
of burying it); on this path MemoryOS has no equivalent, so a pin-style escape
hatch may be worth considering.

We also want to be clear about what we did **not** show. We predicted the
opposite attack — raise the peers' frequencies until the victim is the unique
minimum — and it does not work, for the `add_session` reason above. We report
that as a real property of your mechanism. Manufacturing the neglect end to end
against a live agent (dominating the retrieval channel so queries never reach
the victim) is **not demonstrated** and should not be read as though it were.

## Finding 3 — fenced JSON collapses a batch's topic structure (robustness)

`gpt_generate_multi_summary` in `memoryos-pypi/utils.py:259` parses the model's
reply with a bare `json.loads`. On `JSONDecodeError` it prints
`Warning: Could not parse multi-summary JSON` and returns no themes. The
`else` branch at `updater.py:186` then files the entire batch as **one** session
under a constant summary (`updater.py:189-190`):

```python
fallback_summary = "General conversation segment from short-term memory."
fallback_keywords = []  # Use empty keywords since multi-summary failed
```

Those two fields are then the whole basis of two later decisions, and the
fallback degrades both terms of each. Retrieval scores a session on
`semantic_sim_score + keyword_alpha * s_topic_keywords` (`search_sessions`,
`mid_term.py:330`); the *merge* decision that picks which existing session a new
batch joins scores `semantic_sim + keyword_similarity_alpha * s_topic_keywords`
(`insert_pages_into_session`, `mid_term.py:220`). Every batch that hits the
fallback therefore shares one identical summary embedding and carries no
keywords at all, so it is both harder to retrieve and liable to be merged by a
similarity it did not earn.

The trigger is ordinary rather than adversarial. Many current models wrap JSON
in a ` ```json ` fence by default, and such a reply is valid output that this
parser rejects. So a deployment can lose the topic structure of its mid-term
memory for the whole of a run without anything failing.

We want to be accurate about one thing we got wrong first: **this is logged, not
silent.** An earlier draft of our write-up said "silently substitutes", and said
"several LLM replies" when there is exactly one such call in the package. We
found both errors by reading your source while preparing this note, and have
corrected our paper and benchmark docs. The consequence is if anything sharper
than what we first wrote, because the empty keyword list degrades the second
retrieval term as well as the first.

This blocked our measurement: left in place it prevents the promotion path from
being reached at all. We worked around it by stripping the fence at our client
boundary, purely to restore the behaviour MemoryOS gets from a non-fencing
model. We mention that because the difference between compensating for a model
quirk and lowering a bar until an attack works is the whole of a result's value.

Suggested fix: strip a leading/trailing code fence before `json.loads`, or
retry once with a stricter instruction. Both are a few lines and neither changes
the intended behaviour.
